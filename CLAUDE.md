# NAVALIVAY CRM — инструкции для агентов на этом ПК

> Этот файл дополняет `AGENTS.md`. При расхождении приоритет у правила ниже.

## ⛔ ГЛАВНОЕ ПРАВИЛО: работаем ТОЛЬКО в ветке `Kostya`

**Коммитим и пушим исключительно в ветку `Kostya`.**
**В `main` и `master` — никогда, ни в коем случае.**

### Обязательный порядок действий

```bash
# 1. ПЕРЕД любыми изменениями — проверить ветку
git branch --show-current        # должно вывести: Kostya

# 2. Если не на Kostya — переключиться
git checkout Kostya

# 3. Коммит только на Kostya
git add <files>
git commit -m "тип(область): описание"

# 4. Пуш только в Kostya
git push origin Kostya
```

### Запрещено

- `git push origin main` / `git push origin master`
- `git checkout main` / `git checkout master` ради работы
- merge или rebase в `main` / `master`
- force-push в любую ветку, кроме `Kostya`
- прямой деплой на прод мимо `./ops/prod.sh`

### Почему

Ветка `Kostya` — активная линия разработки клиентского интерфейса (корзина с анимацией,
кэшбэк, быстрые категории). Ветки `main` и `master` отражают production-состояние
и связаны с прод-деплоем: посторонний коммит туда уедет на боевой сервер.

### Локальный запуск

```bash
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
cd /Volumes/Files/CRM_local/server && node dev-server.js   # API :3001
cd /Volumes/Files/CRM_local/frontend && npm run dev        # UI :5173
```

Тестовый клиент в браузере:
```
http://localhost:5173/?telegram_id=100001&username=test_client_1&first_name=Клиент
```

### Тестирование клиентского интерфейса

Подробности — в `docs/dev-telegram-mock.md`. Кратко: локально в `server/.env` должны быть
`NODE_ENV=development` и `ALLOW_INSECURE_TELEGRAM_AUTH=1` — иначе запросы от мока
падают с 401. **Оба флага включать только локально, никогда на проде.**

## Обязательная проверка дизайна после UI-правок

**После любого видимого изменения интерфейса запускать скилл `design-check` — до коммита, на финальной версии файлов.**

Правило действует, когда менялись вёрстка, отступы, цвета, шрифты, состояния компонентов,
модалки, кнопки или видимые тексты — в клиентском приложении и в CRM/админке одинаково.

Не применяется к чисто backend-коду, тестам, миграциям и комментариям без видимых изменений.

Скилл сам определяет поверхность и берёт соответствующий источник истины:
`docs/frontend-design-reference-for-agents.md` для клиента, `docs/crm-design-standards.md`
для CRM. Визуальный язык между этими поверхностями не переносится.

Что проверяется: отступы и шкала, токены темы, состояния и логика (включая закрытие модалок
по `docs/cursor-skill-modal-async-pattern.md`), мобильная адаптация на `393x852`, `375px`, `360px`.

**Границы честности:** статический разбор не измеряет геометрию после рендера. Пункты про
реальные отступы, наложение и переполнение скилл помечает как непроверенные. Не выдавать
их за проверенные и не утверждать, что дизайн чист, если интерфейс не запускался и
скриншотов на целевых размерах нет.

**Порядок для видимых UI-правок:** реализовать → прогнать затронутые тесты → `design-check`
на зафиксированной версии → исправить подтверждённые замечания одним пакетом → повторный
прогон затронутой проверки → коммит в `Kostya`.

Дополнительный UX-разбор для новых сценариев — по `docs/development-workflow-for-agents.md`
и `docs/claude-feedback-ux-improver.md`. Учтите: описанный там агент `ux-improver` в текущем
окружении не установлен, скилл `design-check` его не заменяет.
