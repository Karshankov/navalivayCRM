# Production: деплой, рестарт и логи

Это единственный рабочий регламент для `NavalivayNew`.

## Схема процессов

| Компонент | Диспетчер | Порт |
|---|---|---|
| API + CRM | systemd `navalivay-server` | `8082` |
| Telegram-бот | PM2 `navalivay-bot` | нет |
| Userbot | PM2 `navalivay-userbot` | `8083` |

API отсутствует в PM2. Systemd-unit бота замаскирован и не может запуститься. Выбирать диспетчер вручную не нужно.

## Перед выкладкой

Нужен полный SHA из 40 символов:

```bash
cd /var/www/NAVALIVAY
./ops/prod.sh doctor
./ops/prod.sh plan <полный-SHA>
```

`plan`:

- принимает только коммит из `origin/master`;
- разрешает только fast-forward;
- показывает сборку, установку зависимостей и точные рестарты;
- блокирует неизвестные и инфраструктурные файлы.

## Выкладка

```bash
./ops/prod.sh deploy <полный-SHA>
```

Скрипт сам:

- ставит блокировку от параллельного деплоя;
- проверяет чистоту отслеживаемых файлов и схему процессов;
- обновляется ровно до указанного SHA;
- собирает frontend во временный каталог и атомарно меняет `dist`;
- перезапускает только затронутые компоненты;
- ждёт health до 60 секунд;
- повторно запускает `doctor`.

Неотслеживаемые диагностические файлы не удаляются. Автоматического отката после миграций нет: при ошибке скрипт останавливается и показывает нужные логи.

## Что определяет планировщик

| Изменение | Действие |
|---|---|
| `frontend/**` | сборка frontend, без рестарта |
| код API | рестарт `api` |
| код бота | рестарт `bot` |
| код userbot | рестарт `userbot` |
| общий серверный модуль | рестарт всех точек входа, которые его импортируют |
| серверные зависимости | `npm ci` и нужные рестарты |
| документация и тесты | только обновление файлов |
| неизвестная инфраструктура | отказ до изменения production |

Для удалённых и перемещённых модулей объединяются графы импортов старого и нового коммита.

## Ручной рестарт и логи

После ручного изменения `.env`, Telegram-сессии или proxychains:

```bash
./ops/prod.sh restart api
./ops/prod.sh restart bot
./ops/prod.sh restart userbot
```

Логи:

```bash
./ops/prod.sh logs api
./ops/prod.sh logs bot
./ops/prod.sh logs userbot
```

## Если деплой остановлен

- «грязные отслеживаемые файлы»: не затирать их, сначала выяснить владельца изменений;
- «не fast-forward»: сверить текущий production SHA и историю;
- «инфраструктурный файл»: провести отдельную ручную процедуру с резервной копией;
- health не поднялся: смотреть логи, которые напечатал скрипт; миграции назад автоматически не откатывать.

Если деплой оборвался после обновления Git, повторите `deploy` с тем же полным SHA. Скрипт снова выполнит сохранённый план и удалит защищённый маркер только после успешного `doctor`. Другой SHA до завершения не принимается.

Правила горячих исправлений: [`prod-hotfix-playbook.md`](prod-hotfix-playbook.md).
