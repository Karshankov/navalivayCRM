Глубина code review зависит от риска задачи. Проверяй затронутую область, а не весь проект без причины. Каждое замечание сначала сверяй с задачей, фактическим кодом и правилами проекта. Подтверждённые замечания исправляй одним пакетом и повторно проверяй только затронутую область. Ложные или неприменимые отклоняй с кратким обоснованием. Для обычного и высокого риска продолжай до 0 подтверждённых замечаний.

**Why:** Дмитрий явно попросил это после того как я в задаче «Карточка товара» прогнал ревью один раз, исправил замечания, но не перепроверил — а в требованиях на качество уровня dorogix компаний должна быть гарантия что после правок всё чисто. Один прогон не гарантирует что правки не внесли новых проблем.

**How to apply:**
- Для малого риска с изменением исполняемого кода, настройки или поведения обязателен узкий review изменённой области
- Для чистого текста или CSS без изменения поведения достаточно целевой проверки и итогового UX-разбора
- Для обычного и высокого риска обязателен полный review затронутого сценария
- Если нужны UX и code review, запускать их параллельно на одной зафиксированной версии
- Параллельные проверяющие работают только на чтение; основной агент не меняет файлы до получения обоих отчётов
- Если **есть подтверждённые замечания** любого уровня → исправить → повторить затронутые тесты → **снова** прогнать `code-reviewer`
- Если code review дал **0 подтверждённых замечаний** и все остальные обязательные проверки также завершены без подтверждённых замечаний → коммит → отчёт пользователю «готово»
- Не пропускать подтверждённые «минорные» замечания между итерациями
- Сначала собрать все замечания, затем исправить их одним пакетом и выполнить адресную перепроверку
- Если менялся UI, после любого следующего видимого изменения повторить итоговый UX-прогон

Полная последовательность работы для NAVALIVAY: `docs/development-workflow-for-agents.md`.
