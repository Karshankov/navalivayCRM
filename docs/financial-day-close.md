# Закрытие финансового дня

## Назначение и границы

Мастер открывается в CRM из меню «Действия с заказами» и состоит из трёх шагов: данные терминала, пересчёт наличных, распределение денег. Он сохраняет историю и итоговый отчёт, проводит сверку и расчёты через существующие `cash_accounts` и `cash_transactions` и ставит уведомление в существующий outbox.

Закрытие финансового дня **не завершает рабочую смену сотрудника и не отзывает её токен**. Текст итогового отчёта о закрытии относится к финансовому дню, а не к учёту рабочего времени.

Модуль по умолчанию выключен. Наличие кода, подключённого API и успешных тестов не означает, что миграция применена к рабочей базе или что функция включена в production.

## Расчёты

Все новые расчёты выполняются в целых копейках. Суммы из существующих REAL-полей переводятся в копейки только на границе с финансовым учётом. Ввод сумм допускает точку или запятую и не более двух знаков после разделителя.

Обозначения:

- `K` — баланс существующего счёта кассы перед закрытием; новые наличные и карточные оплаты учитываются на одном счёте.
- `N` — пересчитанные физические наличные, включая монеты и мелкие номиналы.
- `C` — сумма карточных оплат по терминалу, уже полученная владельцем.
- `P` — прибыль дня из общих с Overview финансовых показателей.
- `R` — наличные, оставляемые на следующий день.

Формулы:

```text
Расхождение и подписанная корректировка: D = N + C − K
Передать владельцу физическими наличными: P − C
Одна общая расходная проводка владельцу: P
Перевести на счёт выручки: N − (P − C) − R
Итоговый баланс кассы: R
```

Терминальные наличные — информационный показатель: они уже входят в `N` и второй раз не прибавляются. Недостача или излишек не блокируют закрытие и оформляются одной корректирующей проводкой. Отрицательная физическая выдача владельцу и недостаток наличных для выдачи и остатка требуют исправления исходных данных; суммы не обрезаются до нуля.

Перевод между счетами — связанная пара расхода и прихода. Выручка и прибыль дня не меняются из-за корректировки, выдачи владельцу, перевода или других ручных движений учёта.

Контрольный пример: `K = 3035`, `N = 2535`, `C = 500`, `P = 1500`, `R = 35`, исходный баланс счёта выручки `600` BYN. Расхождение равно нулю; владельцу передаются `1000` BYN наличными; общая расходная проводка владельцу — `1500` BYN; перевод — `1500` BYN. Итоговые балансы: касса `35`, счёт выручки `2100` BYN.

## Бизнес-день и счета

Для согласованного учёта применяется `Europe/Minsk`; перед включением необходимо проверить настройку `BUSINESS_TIMEZONE=Europe/Minsk`. День начинается в местную полночь; верхняя граница следующего дня исключается. В текущем часовом поясе это 21:00 UTC предыдущей календарной даты.

Показатели Overview и закрытия используют один общий запрос: оплаченные заказы со статусами `completed`/`delivered` по `paid_at` и завершённые POS-продажи по `completed_at`. Перенесённый остаток кассы не становится новой выручкой или прибылью.

Автоматический выбор возможен только для единственных активных счетов с названиями «Касса» и «Выручка». При отсутствии или неоднозначности названий оператор выбирает два разных существующих активных счёта. Мастер не создаёт счета автоматически.

## Безопасное включение и исторический переход

**Текущую рабочую базу с обнаруженными ошибками целостности нельзя мигрировать, заменять или автоматически восстанавливать без отдельного согласования.** Созданная резервная копия с теми же ошибками не является проверенной восстановимой копией. Пока проблема не решена и включение отдельно не согласовано, код проверяется только на изолированных тестовых базах.

Порядок подготовки для исправной целевой базы:

1. Отдельно согласовать целевую базу, дату перехода и включение. Для production также требуется отдельное разрешение на развёртывание и перезапуск.
2. Создать согласованную резервную копию SQLite, учитывая WAL, и проверить целостность копии и возможность восстановления. Не копировать только основной файл работающей WAL-базы как гарантированно согласованный снимок.
3. Проверить целостность целевой базы и отсутствие нарушений внешних ключей. Повреждения не исправляются автоматически.
4. Согласовать исходный баланс и карточные суммы переходного дня. Старые записи могут содержать прежнюю схему карточных проводок или ручные корректировки. Их нельзя автоматически пересчитывать или переписывать; предпочтителен первый полный день с новой схемой учёта, с отдельно подтверждённым начальным состоянием.
5. Проверить два целевых счёта, права операторов, часовой пояс и при необходимости подтверждённого получателя отчёта.
6. Только после согласования включить `FINANCIAL_DAY_CLOSE_ENABLED=1` или `true` в конфигурации согласованного процесса. Затем выполнить согласованный запуск или перезапуск, использующий правильный `DATABASE_FILE`.

При старте с включённым флагом `initDb()` сначала выполняет `quick_check` и `foreign_key_check`. Если проверка не пройдена, запуск останавливается с `financial_close_database_invalid` до выполнения миграций внутри `initDb()`. При выключенном флаге финансовая миграция не запускается, а её API после проверки административной авторизации возвращает `503 financial_close_disabled` без обращения к отсутствующим таблицам модуля.

Preflight **не создаёт и не проверяет резервную копию**: это отдельная обязательная эксплуатационная процедура. Финансовая миграция добавляет таблицу истории, связи проводок, индексы и выключенную группу уведомлений; исторические балансы и движения она не переписывает.

Отключение флага не отменяет уже проведённые закрытия. Нельзя удалять историю или связанные проводки для «отката»; исправление финансового результата требует отдельного согласованного решения.

## Права и подтверждение

Операции требуют административной авторизации, действующего доступа к dashboard и, при включённом учёте сотрудников, действующего токена сотрудника. Обычный сотрудник подтверждает закрытие только в своей активной рабочей смене; manager может закрывать финансовый день без активной смены. Доступ повторно проверяется внутри транзакции.

Предпросмотр не записывает финансовые движения. При изменении балансов, финансовых показателей, получателей или бизнес-дня старое подтверждение отклоняется. Если выбранный счёт перестал быть активным, операция также отклоняется.

Финальное подтверждение использует `Idempotency-Key`. История уникальна по бизнес-дате и ключу запроса. История, все проводки, итоговые балансы и задания outbox сохраняются одной immediate-транзакцией. Повтор с теми же данными возвращает сохранённый результат; изменённые данные с тем же ключом дают конфликт. Связанные с закрытием проводки защищены от ручного PATCH и DELETE через финансовый API.

Если ответ подтверждения потерян, интерфейс сохраняет исходный запрос и ключ в `sessionStorage`, блокирует новое закрытие и предлагает проверить сохранённый отчёт или повторить тот же запрос. Нельзя очищать это состояние и отправлять новый ключ, не выяснив результат. Недоступность хранилища блокирует небезопасное подтверждение.

## Отчёт и Telegram

Отчёт и финансовый снимок сохраняются при закрытии. История и отправка используют этот сохранённый отчёт, а не текущие изменяемые балансы или прибыль.

Группа уведомлений `financial_close` первоначально выключена. Настройка выполняется через существующий раздел сотрудников и уведомлений с подтверждением получателя; нельзя угадывать Telegram ID или отправлять финансовые данные случайному адресату.

Если получатель не настроен, закрытие и отчёт сохраняются со статусом `awaiting_recipient`. После настройки постановка сохранённого отчёта в очередь доступна через manager-доступ. Повторная постановка не создаёт ещё одно уведомление и не перенаправляет уже поставленный отчёт при изменении настроек.

Сетевая отправка выполняется существующим worker после коммита. Ошибка Telegram не отменяет финансовое закрытие. Подтверждённый отказ может перейти в retry; неизвестный результат отправки (`unknown`) не отправляется автоматически повторно. Проверки с имитированным отправителем подтверждают работу интеграции, но не являются доказательством фактической доставки в Telegram.

## Проверки

Из каталога [server](../server/) можно запустить изолированные серверные проверки:

```bash
BUSINESS_TIMEZONE=Europe/Minsk node --test \
  tests/financial-close-activation.test.js \
  tests/financial-close-calculations.test.js \
  tests/financial-day-close-service.test.js \
  tests/financial-day-close-routes.test.js \
  tests/financial-close-concurrency.test.js
```

Проверяются формулы, границы дня, статусные фильтры, сохранение истории, права доступа, повторные запросы, откат при ошибках проводок и outbox, доставка через имитированный Telegram, а также реальные гонки двух независимых подключений к временной WAL-базе. Временные базы тестов не являются рабочей базой.

Из каталога [frontend](../frontend/) доступны целевые проверки интерфейса:

```bash
npm run test:unit -- \
  src/components/admin/crm/__tests__/FinancialDayCloseModal.spec.ts \
  src/stores/__tests__/crm.financial-close-api.spec.ts \
  src/utils/__tests__/financialDayClose.spec.ts
npm run type-check
npm run build-only
```

Резервные копии и SQLite WAL/SHM из `server/data/financial-close-backups/` исключены из Git. Это не заменяет контроль конфиденциальности, прав доступа и проверку списка файлов перед коммитом.
